# LedgerLite assumptions and limitations

- One unspecified currency with two decimal places; no currency conversion. API amounts/balances are JSON numbers in major units. Persistence uses integer minor units (cents). Number representations with more than two decimal places, including `0.1 + 0.2` serialized as `0.30000000000000004`, are rejected rather than silently rounded. Clients should submit intended decimal values.
- Each amount and accumulated balance is at most 2,147,483,647 cents (21,474,836.47), matching Prisma's Int range. Credits that exceed the balance cap are rejected atomically. No overdrafts, interest, fees, initial funds, or balance-adjustment endpoint.
- UUID account/transaction IDs and UTC creation times are server controlled. Names need not be unique. Names, descriptions, and references are trimmed. A description is optional and defaults to an empty string. References are case sensitive and unique per account after trimming.
- Strict request schemas reject extra/server-controlled fields. Malformed UUIDs return 400; valid UUIDs that do not exist return 404. Validation is evaluated before account existence. Business conflicts return 409. Errors share the envelope documented in API.md.
- Duplicate references return 409 rather than replaying a previous success. They do not compare payloads or mutate any state. Retry an uncertain request with the same reference; never generate a new reference solely because a response was lost.
- Transaction insertion and balance mutation share a Prisma/SQLite transaction. Mutations acquire the SQLite write lock before reading, and debits use a conditional update. The database uniqueness constraint resolves duplicate races. There is no process-local lock; the independent-client concurrency test exercises database serialization.
- SQLite is appropriate for this local assessment, with a single writer at a time. Sustained contention/transaction timeouts can return 503 and should be retried using the same reference. High-throughput multi-instance deployment would require further database/operations planning. No automatic retry loop is added.
- History uses bounded offset pagination. Timestamps sort descending with descending UUID as a deterministic tie breaker, not an insertion sequence. Count/results are consistent within a request; concurrent inserts can move records between separate page requests.
- Records are immutable through the API. No update/delete route exists. SQL constraints protect value domains, foreign keys, and uniqueness; an operator with direct database access can still alter records or balances. Database access is a trusted boundary, and reconciliation of arbitrary manual SQL changes is outside scope. Use the checked-in migration; `db push` does not preserve custom SQL checks.
- No authentication/authorization was specified, so none is implemented. The server binds localhost by default. This is a local assessment and requires authentication, ownership-based authorization, TLS, rate limiting, and operational controls before public financial use.
- No frontend, deployment infrastructure, queues, double-entry accounting system, account deletion, transaction reversal, or external payment integrations. No currency code was invented. No real secrets are necessary; `.env.example` contains local configuration only.
- Tests use temporary file-backed SQLite with the actual SQL migration; Node's built-in SQLite helper may emit an experimental warning. Tests run serially by file to keep assessment resource use modest. Runtime was verified with Node 24.2.0/npm 11.4.1. Tooling dependencies include pinned patched transitive overrides for the Prisma CLI; the lockfile makes installation reproducible.
- The optional transfer endpoint is implemented after mandatory acceptance passed. A transfer consists of two normal ledger entries and no extra transfer model. The caller supplies a reference unused on both accounts; per-account uniqueness prevents duplicate financial effects. Same-account transfers are rejected. Failure of either balance change or either entry insert rolls back all four writes. A destination balance cap is enforced as for ordinary credits.
