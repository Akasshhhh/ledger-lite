# LedgerLite API

Base URL: `http://127.0.0.1:3000`. Send JSON bodies with `Content-Type: application/json`; maximum body size is 16kb. All timestamps are UTC ISO 8601 strings. UUIDs and timestamps are generated by the server. Money is returned as a JSON number in major units; integer cents are persisted.

## Response conventions

Successful creation: `201`; reads: `200`. Single-resource responses use `{ "data": {...} }`. History uses `{ "data": [...], "pagination": {...} }`. Unknown request body/query keys are rejected on endpoints with schemas. Unknown paths and unsupported transaction update/delete methods return `404`.

Errors consistently use:

```json
{"error":{"code":"INSUFFICIENT_FUNDS","message":"Account has insufficient funds"}}
```

Validation errors additionally include `details`, an array of `{path,message}` objects. Stack traces, raw database errors, and configuration are never returned.

| HTTP | Code | Meaning |
|---|---|---|
| 400 | VALIDATION_ERROR | Invalid/missing fields, invalid UUID, invalid URL encoding, or invalid pagination |
| 400 | INVALID_BODY | Malformed JSON or unsupported JSON charset |
| 404 | ACCOUNT_NOT_FOUND | A syntactically valid account UUID does not exist |
| 404 | NOT_FOUND | Endpoint/method unavailable |
| 409 | DUPLICATE_REFERENCE | Reference already exists for the account |
| 409 | INSUFFICIENT_FUNDS | Debit would overdraw |
| 409 | BALANCE_LIMIT | Credit would exceed 21,474,836.47 |
| 413 | INVALID_BODY | Body exceeds 16kb |
| 500 | INTERNAL_ERROR | Unexpected failure, with all transaction writes rolled back |
| 503 | DATABASE_BUSY | Temporary database contention/transaction timeout; retry with the same reference |

## POST /accounts

Body: `{ "name": "Main account" }`. Name is trimmed, required, and 1–200 characters. Any client-supplied balance, ID, timestamp, or extra key returns `400`.

Response `201`:

```json
{"data":{"id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf","name":"Main account","balance":0,"created_at":"2026-10-28T12:00:00.000Z"}}
```

New balances always start at zero. Account names need not be unique.

## GET /accounts/:accountId/balance

`accountId` must be a UUID. Malformed ID: `400`; missing account: `404`.

Response `200`:

```json
{"data":{"account_id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf","balance":70}}
```

## POST /transactions

```json
{
  "account_id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf",
  "type":"credit",
  "amount":100,
  "description":"Initial deposit",
  "reference_id":"deposit-1"
}
```

- `account_id`: required existing UUID.
- `type`: exactly `credit` or `debit`, case sensitive.
- `amount`: required JSON number, 0.01 through 21,474,836.47 inclusive, with at most two decimal places. Strings, zero, negatives, and excessive precision are rejected. Total account balance has the same maximum.
- `description`: optional string, trimmed, up to 1000 characters, default `""`.
- `reference_id`: required string, trimmed, 1–200 characters; case sensitive, unique within an account.
- Additional fields, including `id`, `created_at`, and `balance`, are rejected.

Response `201`:

```json
{"data":{"id":"9cf20689-0c18-423b-9e0a-5dc8710200f8","account_id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf","type":"credit","amount":100,"description":"Initial deposit","reference_id":"deposit-1","created_at":"2026-10-28T12:00:01.000Z"}}
```

A subsequent `{ "account_id": "...", "type": "debit", "amount": 30, "reference_id": "purchase-1" }` produces a balance of 70. A debit of 150 from a balance of 100 returns `409 INSUFFICIENT_FUNDS`; balance and history stay unchanged.

Repeating `deposit-1` for the same account returns `409 DUPLICATE_REFERENCE`, even if the repeated body differs. It creates no new entry and applies no balance change. The same reference is accepted for another account. Duplicate checking takes priority over insufficient funds/balance limit for an existing reference.

Balance mutation and record insertion are one database transaction; both roll back on any failure. A conditional balance update prevents concurrent overdrafts. No transaction edit/delete endpoints exist.

## GET /accounts/:accountId/transactions

Example: `/accounts/499e609e-57fe-4702-8ce0-77ec58cc1ccf/transactions?type=credit&page=1&limit=20`.

| Query | Default | Accepted values |
|---|---|---|
| type | Both types | `credit` or `debit` |
| page | 1 | Integer 1–1,000,000 |
| limit | 20 | Integer 1–100 |

Pagination strings must consist of decimal digits, with no leading zero, signs, decimals, spaces, or exponent syntax. Repeated and unknown query keys return `400`.

Response `200`:

```json
{
  "data":[
    {"id":"9cf20689-0c18-423b-9e0a-5dc8710200f8","account_id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf","type":"credit","amount":100,"description":"Initial deposit","reference_id":"deposit-1","created_at":"2026-10-28T12:00:01.000Z"}
  ],
  "pagination":{"page":1,"limit":20,"total":1,"total_pages":1}
}
```

`total` counts matching records for this account and filter. Empty results have zero total pages. A page beyond the last page returns an empty array with unchanged totals. Rows sort by `created_at DESC`, then `id DESC` for deterministic timestamp ties. Count and rows are read together within one database transaction. Separate page requests can see new entries inserted between requests; offset pagination is not a multi-request snapshot. Missing accounts return `404`, even if no history exists.

## POST /transfers (bonus)

```json
{
  "source_account_id":"499e609e-57fe-4702-8ce0-77ec58cc1ccf",
  "destination_account_id":"ce3594e6-359a-499c-8c64-07c183d0ef83",
  "amount":30,
  "reference_id":"transfer-1",
  "description":"Move funds"
}
```

Both UUIDs must identify existing, different accounts. Amount, reference, and optional description follow the transaction validation rules. A reference must be unused in both participating accounts, including references used by ordinary transactions.

Response `201` is `{ "data": { "source_transaction": { ... }, "destination_transaction": { ... } } }`. Each value is a complete transaction object as documented above: the source is a debit, the destination is a credit, and both have the same amount, reference, description, and timestamp, with distinct IDs. Both appear in their account histories. There is no additional transfer table/ID.

Starting balances of 100 and 50 become 70 and 80 after a transfer of 30. Both balance changes and both history entries share one transaction. Missing accounts return `404`; insufficient source funds, a duplicate reference on either side, or a destination balance overflow return `409`; same-account transfers return `400`. Every failure rolls back all changes, including a failure inserting the second ledger entry. Repeating a successful transfer returns `409 DUPLICATE_REFERENCE` without moving funds again. Reusing the reference for a completely different pair of accounts is permitted.
